# Standards adoption RFC

**Research date:** October 14, 2026 (America/New_York). **Status:** research complete; implementation proposed. This document is the canonical RFC for [issue #3](https://github.com/mlg151/henchman-ai/issues/3). Its gap analysis describes the inspected baseline; the adoption phases below remain future implementation work. It does not claim the proposed integrations have shipped.

**Repository baseline:** [main at `b2ab5e5`](https://github.com/mlg151/henchman-ai/commit/b2ab5e507cb68cc072095a9230998aef6dd45712). The original research checkout was `d60e6fb`; its additional commits only changed CI, and the inspected source, tests, docs, roadmap, and dependency files matched this main baseline. Source links below are pinned to that baseline so later implementation changes do not rewrite this research evidence.

## Recommendation and scope

Keep the existing provider, tool, and internal delegation interfaces. Add protocol adapters at those boundaries: **MCP for tools/context; A2A for independent remote agents; OpenTelemetry/OTLP for observability; JSON Schema 2020-12 for canonical tool contracts with explicit provider projections.** Prioritize compatibility and validation before adding remotely exposed servers.

This ordering follows the repository's [foundations-first workflow](https://github.com/mlg151/henchman-ai/blob/b2ab5e507cb68cc072095a9230998aef6dd45712/AGENTS.md#L3) and [current roadmap](https://github.com/mlg151/henchman-ai/blob/b2ab5e507cb68cc072095a9230998aef6dd45712/FEATURE_TODO.md#L1). The phases below are proposed sequencing, not approved delivery dates.

## MCP adoption details

The current MCP revision is a meaningful compatibility boundary: **2026-07-28 removes the initialization handshake and protocol sessions**, carries version/capability metadata per request, and introduces `server/discover`. Change notifications use `subscriptions/listen`; multi-round-trip results carry input requests. Tasks are an optional extension. New implementations should avoid the deprecated roots, sampling, and protocol logging features. [Versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [revision changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

Use the official SDK's supported compatibility behavior rather than reimplementing wire negotiation. Specify supported protocol revisions in a test matrix; unsupported versions must produce actionable errors. Review the SDK migration for changed imports, snake_case Python fields, validation, and error behavior. The existing `mcp>=1.0` requirement can resolve a breaking major on a fresh install: add a tested major-version bound as the first dependency task, then update it with the migration. [SDK migration](https://py.sdk.modelcontextprotocol.io/migration/).

Preserve both text and typed/structured tool results; retain output schemas and metadata, validate structured output, follow pagination, and refresh discovery without expanding agent allowlists. Add resources and user-selected prompt templates through explicit runtime/UI paths. Treat descriptions, prompts, resource contents, and annotations as untrusted input. [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), [protocol primitives](https://modelcontextprotocol.io/specification/2026-07-28).

For HTTP, implement the revision's transport headers, JSON/SSE response handling, cancellation, endpoint validation, and OAuth discovery/PKCE/resource scoping through supported SDK helpers. Keep stdio process-environment auth separate. Bind any future local HTTP server to loopback by default, validate Origin, and expose only an explicit tool allowlist through existing authorization. Broken connections and timeouts must not automatically replay side-effecting calls. [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

## A2A adoption details

A2A complements MCP by connecting independent agent applications. Start with explicitly configured HTTPS destinations and a single SDK-backed HTTP binding. Agent Cards advertise skills, interfaces, versions, capabilities, and authentication requirements; discovery can use `/.well-known/agent-card.json` or direct configuration. Cards are metadata, not permission grants or executable instructions. [MCP comparison](https://a2a-protocol.org/v1.0.1/topics/a2a-and-mcp/), [discovery](https://a2a-protocol.org/v1.0.1/topics/agent-discovery/).

Map both direct Messages and stateful Tasks. Keep remote task/context IDs separate from local run/session IDs. Cover interrupted states, terminal outcomes, bounded polling, artifacts, and cancellation races; cancellation is a request, not a rollback guarantee. Add advertised SSE streaming after polling works, with tested reconnect and partial-artifact handling. [Task lifecycle](https://a2a-protocol.org/v1.0.1/topics/life-of-a-task/), [streaming](https://a2a-protocol.org/v1.0.1/topics/streaming-and-async/), [specification](https://a2a-protocol.org/v1.0.1/specification/).

Restrict card/interface/artifact destinations and redirects, prevent SSRF, scope credentials to approved origins, and enforce task ownership. Remote agents must not expand local tool permissions. Defer webhook push, public catalogs, federation, and inbound serving until the client boundary is verified.

Do not build a separate IBM/BeeAI Agent Communication Protocol adapter: that ACP project merged into A2A and its repository is archived. Distinguish it from other projects named ACP. AGNTCY may complement identity/discovery/messaging later; its A2A-over-SLIM binding is experimental. [ACP status](https://agentcommunicationprotocol.dev/introduction/welcome), [archived ACP](https://github.com/i-am-bee/acp), [SLIM binding status](https://docs.agntcy.org/slim/slim-a2a/).

## OpenTelemetry, evaluation, and schemas

**Tracing:** instrument existing run/provider/tool/delegation boundaries with OTel spans and OTLP export, preserving causal parentage and W3C trace context across approved remote boundaries. Record operation, model, durations, available usage, outcome/error/cancellation, and correlation IDs. Do not fabricate missing usage or equate final-response usage with whole-trajectory cost. Reuse the existing [metrics models](https://github.com/mlg151/henchman-ai/blob/b2ab5e507cb68cc072095a9230998aef6dd45712/src/henchman/metrics/models.py#L20) and [observability integration points](https://github.com/mlg151/henchman-ai/blob/b2ab5e507cb68cc072095a9230998aef6dd45712/src/henchman/ops/observability.py#L52).

GenAI conventions moved to a [dedicated repository](https://opentelemetry.io/docs/specs/semconv/gen-ai/) and are still Development. Pin the mapping to inspected commit [`f3c6d0c`](https://github.com/open-telemetry/semantic-conventions-genai/blob/f3c6d0c9bb66ebd474668a3a0be25c61226f02c2/docs/gen-ai/README.md); recheck upstream before implementation. OTLP export is opt-in; disable prompt, instruction, response, and tool argument/result capture by default, redact before persistence/export, and bound cardinality and payload sizes. An unavailable exporter must not break CLI execution. [OTLP](https://opentelemetry.io/docs/specs/otlp/), [content capture guidance](https://github.com/open-telemetry/semantic-conventions-genai/blob/f3c6d0c9bb66ebd474668a3a0be25c61226f02c2/docs/gen-ai/gen-ai-spans.md#capturing-instructions-inputs-and-outputs), [W3C Trace Context](https://www.w3.org/TR/trace-context/).

**Evaluation:** the Development `gen_ai.evaluation.result` event can report scores and correlation, but it is not a benchmark interchange or evaluator execution standard. Keep a versioned Henchman JSON/JSONL evaluation artifact containing dataset/case/version, evaluator/rubric/version, score scale and direction, thresholds, independent pass/fail evidence, source revision, model/config/tool-contract fingerprints, and trace/run linkage. Provide adapters for specific benchmark harnesses only after round-trip validation. Build on the [existing evaluation framework and its stated limitations](https://github.com/mlg151/henchman-ai/blob/b2ab5e507cb68cc072095a9230998aef6dd45712/evals/README.md#L154). [OTel evaluation event](https://github.com/open-telemetry/semantic-conventions-genai/blob/f3c6d0c9bb66ebd474668a3a0be25c61226f02c2/docs/gen-ai/gen-ai-events.md).

**Schemas:** choose [JSON Schema 2020-12](https://json-schema.org/draft/2020-12) for a versioned canonical tool contract with input/output schemas, provenance, and execution policy. Validate schemas at registration and arguments/results at execution boundaries. Disable network reference resolution by default and bound complexity. Preserve original schemas while generating explicit provider-specific projections and diagnostics for unsupported keywords. [MCP dialect rules](https://modelcontextprotocol.io/specification/2026-07-28/basic#json-schema-usage).

OpenAI strict tools require closed objects and all properties required, with nullable fields used for optional values; Anthropic also supports strict tools, but its subset and optional-property rules differ. Do not apply one vendor's normalization globally. Missing and null arguments have different meanings: adapters need explicit normalization rules that preserve canonical omission/null semantics, or reject ambiguous mappings, together with canonical runtime validation. OpenAI-compatible endpoints (including DeepSeek, Ollama, and OpenRouter configurations) need tested endpoint/model profiles, not an assumption that API similarity implies identical schema support. [OpenAI strict mode](https://developers.openai.com/api/docs/guides/function-calling#strict-mode), [OpenAI supported subset](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas), [Anthropic strict tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use), [Anthropic limitations](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations).

## Phased implementation roadmap

All items below remain **implementation work**. Each phase should ship with focused tests and nearest-reference documentation; maintain roadmap state and changelog when behavior changes.

- [ ] **P0 — Compatibility baseline and dependency bounds.** Record supported protocol/SDK versions, add a tested MCP major bound, and establish offline fixtures. Harmonize the effective settings model and legacy MCP config type when extending transport settings. **Exit:** locked and fresh installations import and pass existing checks; capability reporting identifies tested support rather than installed packages.
- [ ] **P1 — Canonical schemas and MCP client fidelity.** Introduce input/output validation and provider projection diagnostics; retain typed/structured results and metadata; cover pagination and discovery refresh. **Exit:** fixtures cover missing/null, nested definitions/references, recursion, unions, constraints, malformed arguments, scalar/array/null outputs, output-schema errors, and provider rejection paths. Tool scopes survive catalog updates.
- [ ] **P2 — Modern MCP transport/auth/context.** Migrate SDK with explicit legacy/current protocol tests; add Streamable HTTP, OAuth integration, resources, and prompt retrieval. Keep stdio working. **Exit:** independent test servers exercise modern and supported legacy paths, JSON/SSE, headers, auth discovery/PKCE/issuer/resource checks, interruption, cancellation, timeouts, malicious metadata, and cleanup. No blind retry of mutating calls.
- [ ] **P3 — Opt-in telemetry and evaluation artifacts.** Add spans/context propagation, pinned GenAI mapping, OTLP export, and versioned local evaluation exports. **Exit:** in-memory exporter/collector tests verify parentage, usage accuracy, failures/cancellation, score correlation, content-off defaults, redaction, and exporter failure isolation; evaluation artifacts round-trip with their rubric and evidence.
- [ ] **P4 — Outbound A2A pilot.** Add configured remote-agent adapter using pinned released spec/SDK and one binding; handle cards, direct messages/tasks, polling, artifacts, interrupted states, and cancellation before SSE. **Exit:** independent agent implementation plus applicable pinned [A2A TCK](https://github.com/a2aproject/a2a-tck)/[ITK](https://github.com/a2aproject/a2a-itk) coverage; negative tests for versions, extensions, task ownership, destination changes, credential leakage, terminal-state transitions, oversized content, and reconnect races.
- [ ] **P5 — Controlled inbound serving.** Expose an allowlisted MCP server through existing registry authorization; evaluate an A2A server only after the outbound pilot proves useful. **Exit:** independent clients exercise discovery, schemas, result fidelity, and cancellation; unauthorized tools/resources/tasks stay inaccessible. No arbitrary builtin catalog or workspace export.

**Guardrails throughout:** new project writes target `.henchman/`; legacy casing stays read-only. Preserve the `config view/get/set/unset/import/export` contract and file-based settings import/export. Protocol credentials, data access, and telemetry export do not introduce backend settings sync. Discovery/help remains derived from the [shared capability matrix](https://github.com/mlg151/henchman-ai/blob/b2ab5e507cb68cc072095a9230998aef6dd45712/src/henchman/cli/commands/discovery_capabilities.py#L1) and only wired implementations are advertised.

**Deferred decisions:** exact SDK pins are selected during P0 against the test matrix; JSON-RPC versus HTTP+JSON for the initial A2A binding is selected by the pilot; benchmark-specific adapters require a named consumer. Federation, public registries, experimental transports, webhook push, and deprecated MCP features are outside the initial implementation.

## Research validation and completion

At the research baseline, the focused existing checks passed **78 tests**:

```sh
uv run --locked --extra dev python -m pytest --no-cov tests/mcp tests/contracts/test_mcp_contracts.py tests/providers/test_required_tool_schemas.py -q
```

These are local unit/contract regression checks, including mocks and doubles; they do not prove real transport interoperability, OAuth correctness, complete JSON Schema support, or external protocol conformance. No implementation changes were made during this research. This historical check is not a claim that the future adoption phases pass interoperability tests.
